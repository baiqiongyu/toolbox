# 和兴国际物流 · 内部工具平台 — 开发总结报告

> 项目周期：2026-05-23（一日内完成初版）
> 技术栈：PHP 8.4 + Laravel 11 + MySQL + Docker + Tailwind CSS

---

## 一、项目概述

公司内部工具平台，集成了 PCC 通关编码校验、乐天物流轨迹查询、韩国海关清关轨迹查询、华磊物流轨迹查询等工具。所有工具必须登录后使用，支持可配置化的工具首页图标网格，新增工具只需在数据库 `tools` 表加一条记录。

## 三、使用技术详情

### 3.1 后端

| 技术 | 用途 |
|------|------|
| **Laravel 11** | 整体框架、路由、ORM、Blade 模板、表单验证 |
| **Breeze (Blade)** | 登录认证脚手架（注册已关闭，仅保留登录） |
| **PhpSpreadsheet** | 读写 Excel 文件（PCC 工具上传/下载） |
| **Laravel HTTP Client** | 调用外部 API（Rakuten Customs、HuaLei） |
| **原生 curl** | 兼容韩国海关 UNI-PASS 的 SSL（Laravel HTTP Client 在某些 SSL 配置下失败时使用） |
| **Cache** | 缓存任务状态（PCC 校验进度轮询） |
| **dispatch()->afterResponse()** | 后台异步执行（不阻塞请求，前端轮询进度） |
| **MySQL 8.0** | 用户、工具配置、会话等数据存储 |

### 3.2 前端

| 技术 | 用途 |
|------|------|
| **Blade** | PHP 模板引擎，所有页面服务端渲染 |
| **Tailwind CSS** | 原子化 CSS 框架（通过 Laravel Vite 构建） |
| **Vite** | 前端构建工具 |
| **CSS 原生** | 部分精细样式直接写在 `<style>` 中（因为页面是独立 Blade，未抽取公共 CSS） |
| **原生 JavaScript** | 所有交互逻辑用原生 JS，无前端框架 |

### 3.3 Docker

```yaml
services:
  nginx:    # Nginx 反向代理（端口 8082）
  app:      # PHP 8.4-FPM + Composer
  mysql:    # MySQL 8.0（端口 3309）
```

所有源码通过 volume 挂载到容器内，本地修改即时生效。

## 四、开发历程与踩坑记录

### 4.1 第一阶段：环境搭建（耗时最长）

**遇到的问题：**

1. **Docker 目录权限问题**
   - Laravel 项目通过 `composer create-project` 在容器内创建，文件属主为 `root`
   - 在 WSL 中无法直接编辑容器创建的文件
   - **解决**：`sudo chown -R lijiwei:lijiwei ~/toolbox/src`
   - 每次 `docker compose exec app php artisan ...` 创建的文件都需要重新 `chown`

2. **Storage 权限问题（反复出现）**
   - `storage/` 和 `bootstrap/cache/` 目录需要 PHP-FPM（www-data）有写入权限
   - Laravel 的 Blade 编译、日志写入、Session 都依赖这些目录
   - **解决**：每次 `migrate:fresh --seed` 或文件重建后，必须执行：
     ```bash
     docker compose exec app chown -R www-data:www-data /var/www/html/storage /var/www/html/bootstrap/cache
     ```

3. **Node.js 构建问题**
   - PHP 镜像里没有 Node.js，`npm install`/`npm run build` 需要在宿主机（WSL）执行
   - 编译产物对 `public/build/` 目录没有写入权限（root 创建）
   - **解决**：宿主机安装 Node，`sudo chown` 后再 `npm run build`

4. **APP_KEY 问题**
   - 重写 `.env` 文件时误用了 `base64_SOMEKEY` 占位符
   - Laravel 启动报错：`Unsupported cipher or incorrect key length`
   - **解决**：`php artisan key:generate`

### 4.4 第四阶段：PCC 通关编码校验

**核心流程：**
1. 用户上传 Excel 文件（A:PCC, B:韩文名, C:电话, D:邮编, E:英文名）
2. 后端解析 Excel，创建任务（存入 Cache）
3. 通过 `dispatch(Closure)->afterResponse()` 后台异步处理
4. 逐条调用韩国海关 UNI-PASS API 校验
5. 前端每 1.5 秒轮询 `/status/{taskId}` 获取进度
6. 完成后显示结果，支持通过/失败 Excel 分别下载

**遇到的问题：**

1. **PhpSpreadsheet 需要 zip 扩展**
   - `composer require phpoffice/phpspreadsheet` 时提示 `ext-zip missing`
   - **解决**：Dockerfile 加入 `libzip-dev` 和 `docker-php-ext-install zip`
   - 事后需要 `docker compose restart app` 让 PHP-FPM 加载新扩展

2. **dispatch()->afterResponse() 的闭包问题**
   - PHP 闭包中使用 `$this`（指向控制器）可能无法序列化
   - `sync` queue + `afterResponse()` 不需要序列化，工作正常
   - **注意**：如果切到 `database` queue，闭包需要改成 Job 类

3. **前端变量名错误 debug 3 小时**
   - `const rs = document.getElementById('resetBtn')` ← `rs` 是重置按钮
   - `const rss = document.getElementById('resultsSection')` ← `rss` 才是结果区域
   - 代码里全用 `rs.style.display` 来控制结果区显示/隐藏
   - 实际控制的是重置按钮，结果区一直 `display: none`
   - **教训**：变量命名要清晰，`rs`/`rss` 太容易混淆

4. **CSRF 问题**
   - POST 请求没带 `Accept: application/json` 头
   - Laravel 验证失败后返回 HTML 而不是 JSON
   - **解决**：fetch 加一行 `'Accept': 'application/json'`

### 4.5 第五阶段：乐天物流轨迹查询

**最开始犯的错误：**
- 以为是日本 Rakuten，用网页爬虫方式解析 HTML
- 用户纠正：是韩国 Lotte Global Logistics（롯데택배）
- 用户提供了现成的 API Client 代码

**实际 API：**
```
POST https://ftr.alps.llogis.com:18260/openapi/ftr/getPaclTrackingTp01
Headers:
  Authorization: IgtAK eyJhbGciOiJIUzI1NiJ9...
  charset: utf-8
Body:
  INV_NO: 单号
  SUPER_CUST_CD: LGLCBE
Response:
  code: "S" 表示成功
  TRACK_LIST[0].TRACKING[] → 轨迹数组
```

**轨迹字段：**
- `SCAN_YMD` — 日期 (20260522)
- `SCAN_TME` — 时间 (112817)
- `GODS_STAT_NM` — 状态码（집하, 셔틀발송, 배달전, 배달완료...）
- `STATUS` — 状态描述（"물품을 보내셨습니다."）
- `BRNSHP_NM` — 操作网点

**坑**：Laravel HTTP Client 设置 `verify => false` 时，某些服务器需要额外 SSL 配置。这里的 API 工作正常。

### 4.6 第六阶段：清关轨迹查询

**API：**
```
GET https://unipass.customs.go.kr:38010/ext/rest/cargCsclPrgsInfoQry/retrieveCargCsclPrgsInfo
Params: crkyCn, hblNo(提单号), blYy(年份)
```

**大坑：韩国海关 API SSL 连接问题**
- 容器内 curl 时显示 `TLSv1.3 (OUT)` → 服务器不支持 TLS 1.3，重置连接
- 加 `--tlsv1.2` 依然无效（curl 版本问题，忽略 `--tlsv1.2`）
- 最终方案：原生 curl 设置 `CURLOPT_SSLVERSION = CURL_SSLVERSION_TLSv1_2` + `CURLOPT_SSL_CIPHER_LIST = 'DEFAULT@SECLEVEL=1'` + `CURLOPT_SSL_ENABLE_ALPN = false`
- API 间歇性断连，加了重试逻辑（最多 3 次）

**XML 解析踩坑：**
- 实际返回的 XML 结构跟我猜测的完全不同！
- `cargCsclPrgsInfoQryVo` — 主单信息（商品名、当前状态、海关）
- `cargCsclPrgsInfoDtlQryVo[]` — 详细轨迹（这才是需要的）
- 字段：`prcsDttm`（时间）、`cargTrcnRelaBsopTpcd`（状态）、`shedNm`（场所）、`rlbrCn`（备注）

**状态翻译迭代：**
- 初始只写了 20 多个映射，很多状态没翻译
- 通过 debug log 捕获未翻译状态，逐步补充到 60+ 个

### 4.7 第七阶段：华磊物流轨迹查询

**API：**
```
POST https://sapi.e-kc.vip/HLApi/queryTrackList
Body: {"documentCode": ["单号"]}
Response: {"status":200,"data":[{"trackingNumber":"...","trackDetails":[...]}]}
```

**坑：JSON 二次编码**
- API 返回的 body 是 `"{\"status\":200,\"data\":[...]}"`（字符串套 JSON）
- Laravel `$response->json()` 只解一次，拿到的是字符串不是数组
- **解决**：手动 `json_decode()`，如果结果是 string 就再解一次

**数据过滤：**
- 过滤掉 `track_content === "货物电子信息已经收到"` 的无意义节点
- 按 `track_date` 时间升序排列

**API 偶发空返回**：
- 有时同一个单号第一次查返回空，第二次就正常
- 加重试逻辑解决

## 五、数据库结构

### tools 表（工具配置）

```sql
CREATE TABLE tools (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    name         VARCHAR(100) NOT NULL COMMENT '工具名称',
    icon         VARCHAR(50) NOT NULL COMMENT '图标 emoji',
    route        VARCHAR(100) NOT NULL COMMENT '路由 /tools/xxx',
    color        VARCHAR(20) DEFAULT '#3498db' COMMENT '图标背景色',
    description  TEXT COMMENT '工具描述',
    enabled      TINYINT(1) DEFAULT 1 COMMENT '是否启用',
    sort_order   INT DEFAULT 0 COMMENT '排序',
    created_at   TIMESTAMP,
    updated_at   TIMESTAMP
);
```

新增工具只需 INSERT：

```sql
INSERT INTO tools (name, icon, route, color, description, sort_order) 
VALUES ('工具名', '🚚', '/tools/xxx', '#059669', '描述', 5);
```

## 六、部署注意事项

1. **Docker 端口**
   - Nginx: 8082（跟 wms 的 8081 错开）
   - MySQL: 3309（跟本机 MySQL 3306 和 wms 3308 错开）

2. **服务器上线**
   - 服务器装 Docker + docker-compose-plugin
   - `git clone` 或 `rsync` 代码
   - `docker compose up -d` 启动
   - 域名 `inspection.e-kc.com` 反代到 8082（或 nginx 容器端口映射到 80）

3. **每次迁移/重建后必做**
   ```bash
   chown -R www-data:www-data storage/ bootstrap/cache
   ```

4. **新建用户**
   ```bash
   php artisan user:create 用户名 邮箱 密码
   ```

## 七、经验教训总结

1. **API 集成先确认接口文档** — 乐天一开始我就猜错了（以为是日本 Rakuten 实际是韩国 Lotte），清关接口字段名也猜错了，浪费大量时间。
2. **CSS 变量名要规范** — `rs` 和 `rss` 只差一个字母，debug 三小时才发现。
3. **Docker 权限是 Laravel 开发最大坑** — 文件属主混乱导致的各种奇怪问题（写入失败、编译失败）。
4. **韩国政府 API SSL 兼容性差** — 需要 TLS 1.2 + 特定 cipher + 关掉 ALPN，原生 curl 比 Laravel HTTP Client 更可控。
5. **前端设计先问用户喜好** — UI 迭代了 5+ 版本才定稿，每次都是全量重写，效率极低。
6. **配置文件化优于写死** — `tools` 表设计得很好，新增工具只需一条 SQL，不用改任何代码。
7. **调试日志是好帮手** — 通过 `Log::debug` 捕获未翻译状态码、API 原始返回值，快速定位问题。
